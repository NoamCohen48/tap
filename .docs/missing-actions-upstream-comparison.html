Engineering decision brief · device actions

Fill the action gaps without losing Tap’s character.

A comparison of Tap’s missing Android actions against Appium UiAutomator2, Maestro, openatx/uiautomator2, agent-device, and AndroidX UiAutomator 2.4. The goal is not feature-count parity. It is a small, deterministic action model with explicit outcomes.

Branch feat/device-actions Base 56dee2f Independent implementation API 26+
01 / Decision

Build the useful actions. Reject the escape hatches.

The upstream review strengthens Tap’s original direction. Mature tools prove these capabilities are feasible, but they also reveal the cost of generic coordinate APIs, implicit recovery, positional dialog guesses, and unmanaged device-global state.

Build first

Deterministic core

Rotation, deep links, background/foreground, screen power, typed permission prompts, double tap, drag, pinch, and fling.

Build later

Managed environment

Per-app locale, media injection, and mock location. Each needs explicit ownership, verification, and cleanup.

Do not expose

Raw coordinates

Coordinates can remain an internal consequence of resolving a selector, never the public identity of a Tap action.

Do not promise

Secure unlock

Tap should wake and inspect screen state, but never store a PIN, password, or unlock pattern.

Separate phase

WebView and Compose

These are automation backends or app integrations, not individual gestures. Keep them out of the core action expansion.

The most useful upstream lesson comes from agent-device’s drag design: resolve every endpoint before dispatch, author the full gesture as one bounded mutation, and refuse an impossible plan before input. The most useful warning comes from Maestro’s auto-verification flow: a convenience must not silently tap chooser or browser dialogs behind the test’s back.

03 / Constraints

Rules every new action must obey.

One authored mutation

Double tap, drag, pinch, permission response, and rotation each cross the protocol as one operation. Never compose a gesture from replayable client calls.

Resolve before the gate

Every selector involved in a mutation—including both drag endpoints—must resolve exactly once before any pointer goes down.

Verify the postcondition

Rotation waits for the display, deep links inspect launch results, and device-state changes read back the state. “Command accepted” is not enough.

Represent uncertainty

If transport or ADB ownership is lost after acceptance, return INDETERMINATE. Never infer that an unconfirmed mutation did not happen.

No hidden input

No automatic chooser tap, no permission watcher, no implicit retry, and no settle that silently mutates the UI.

Own global state

Rotation lock, locale, mock location and injected media need captured initial state, bounded cleanup, and evidence when restoration cannot be proven.

04 / Comparison

Action-by-action findings.

04.1

Rotation

Build first
Appium
The on-device server calls UiAutomation.setRotation, polls the observed rotation every 100 ms, and fails when the display does not reach the request. This is the strongest implementation pattern in the set.
Maestro
Disables accelerometer_rotation, writes numeric user_rotation, then its higher layer waits for app settling. The mapping assumes rotation 0 is portrait, which is not universal on landscape-natural devices.
uiautomator2
Exposes natural, left, right and upside-down plus explicit freeze/unfreeze. It cleanly separates choosing a rotation from releasing the sensor lock.
agent-device
Uses the settings approach but improves it with a 15-second dumpsys display poll and an explicit error when an app pins orientation.
AndroidX 2.4
Provides freeze/unfreeze and natural/left/right, plus geometry-aware portrait/landscape helpers. Its source explicitly warns that natural orientation differs between phones and tablets.

Tap proposal

  • Use the on-device AndroidX / UiAutomation path, not raw settings as the primary implementation.
  • Expose portable setOrientation(PORTRAIT | LANDSCAPE) and exact setDisplayRotation(NATURAL | LEFT | UPSIDE_DOWN | RIGHT), plus unfreezeRotation().
  • Poll displayRotation and dimensions until the requested state is observed; an app-pinned orientation is a typed failure.
  • Capture the session’s initial lock/rotation state and restore it during teardown. Restoration failure must be visible, not best-effort silence.
device.setOrientation(Orientation.LANDSCAPE)
device.setDisplayRotation(DisplayRotation.RIGHT)
device.unfreezeRotation()
04.2

Power and lock state

Build narrowly
AndroidX
wakeUp() and sleep() are direct device operations; wake adds a short delay only when the screen actually changed.
uiautomator2
Maps screen_on/screen_off to wake/sleep. Its unlock() is a power key plus diagonal swipe, useful for a swipe keyguard but not a secure unlock contract.
Appium
Offers lock-state and unlock strategies in its shared Android driver. That breadth also brings credential provisioning and OEM-specific complexity.
Tap today
Attachment already wakes and dismisses a non-secure keyguard internally, but clients cannot inspect or change screen power explicitly.

Tap proposal

  • Add screenState(), wake() and sleep(), with read-back verification.
  • Expose dismissKeyguard() only for non-secure keyguards and return a specific “secure keyguard” refusal.
  • Do not accept PINs, patterns or passwords. Secure test-device provisioning stays outside Tap.
04.3

Deep links

Build first
Appium
mobile: deepLink delegates to ADB URI launch, accepts an optional package, and can wait for launch completion.
Maestro
Runs an ACTION_VIEW intent. Its optional auto-verification can tap chooser and Chrome agreement UI; convenient, but those are hidden mutations Tap should not copy.
uiautomator2
open_url is the minimal form: am start -a VIEW -d URI.
agent-device
Treats URL opening as navigation and supports app-scoped and URL-only forms.

Tap proposal

  • Add a streamed-safe, typed host operation: app.openLink(uri, target = AUT, waitForLaunch = true).
  • Pass ADB arguments as an argv list, never a shell-quoted command string.
  • Return resolution/launch facts and optionally verify that the AUT owns the focused window.
  • Never tap an app chooser automatically. Tests may select it through explicit system-scoped selectors.
app.openLink("shop://product/42")
app.openLink("https://shop.example/p/42", target = LinkTarget.AUT)
04.4

Background and foreground

Build convenience
Appium
backgroundApp(seconds) can block for a duration and restore the app. A negative duration leaves it backgrounded.
Maestro
Uses explicit pressKey: home, then launchApp(stopApp: false) to return the existing task to the foreground.
Tap today
pressHome() and app.launch() already provide the primitives, but callers must know the intended composition.

Tap proposal

  • Add verified app.background() and app.foreground() as readable lifecycle operations.
  • Background verifies only that the AUT no longer owns the focused window. Android is allowed to kill a background process.
  • Foreground does not promise process identity; callers can compare process() when that matters.
  • Do not add a blocking backgroundFor. Explicit test-language delay or a domain condition is clearer.
04.5

Permission prompts

Build typed
Appium
Detects regular versus permission alerts from resource-ID patterns, prefers allow/deny IDs, accepts an optional label, then falls back to button position. The patterns are valuable; the positional fallback is not.
AndroidX 2.4
Ships a PermissionDialog watcher with allow/deny IDs. It is small but Google-controller-specific, and the watcher model performs unattended input.
agent-device
Uses one-shot alert get/wait/accept/dismiss. It explicitly never replays an unconfirmed response and tells callers to verify app state separately.
Maestro
Primarily configures permission state directly rather than modeling every visible permission choice.

Tap proposal

  • Keep app.grantPermission() for setup. Add a separate, visible-prompt API for testing the dialog itself.
  • Inspect and return typed available choices: while-using, one-time, always, approximate, deny and deny-without-asking-again where present.
  • Choose by known resource ID for the active permission-controller package. Never fall back to “second button.”
  • Send the response once, then observe the prompt transition. An unconfirmed result is INDETERMINATE, not a retry.
val prompt = device.permissionPrompt().await()
prompt.choose(PermissionChoice.WHILE_USING)
04.6

Double tap

Build
Appium
Implements double click as one server command, targeting an element, a locator resolved at execution time, or coordinates.
uiautomator2
Performs two coordinate clicks separated by a configurable duration.
Tap lesson
Two client-side tap() calls are not equivalent: the first can change the screen, and transport uncertainty between calls breaks the meaning of “double tap.”

Tap proposal

  • Add element.doubleTap() as one driver mutation after one exact selector resolution.
  • Use Android’s double-tap timing bounds internally. Avoid a public interval until a real use case needs it.
  • Return no claim about app response; the test asserts the resulting state.
04.7

Drag and drop

Build carefully
AndroidX
UiObject2.drag starts at the object’s visible center and moves to a point at a pixel-per-second speed.
Appium
Supports element or coordinate origins and coordinate destinations, with density-scaled speed.
uiautomator2
Its selector object can drag to coordinates or another selector.
agent-device
Has the best contract for Tap: source and destination selectors/refs are both resolved before dispatch; hold, move and destination-hold phases form one bounded gesture.

Tap proposal

  • Add source.dragTo(destination). The protocol command carries two selectors.
  • Resolve both to exactly one visible node before the mutation gate; retain them only within this command and recycle both afterward.
  • Model activation hold, movement duration and optional destination hold. Cap total gesture duration.
  • Add directional element-relative drag only if a concrete product needs it; selector-to-selector is the durable first primitive.
device.element(res("card_42"))
    .dragTo(device.element(res("archive_zone")))
04.8

Pinch and zoom

Build element-relative
AndroidX
pinchOpen/pinchClose operate inside visible element bounds, validating 0–1 percent and speed.
Appium
Exposes the same percent-and-speed model for either an element or a rectangular coordinate area.
agent-device
Uses scale around a coordinate center and supports combined two-finger transforms. It warns that recognizers may not report exact requested values.

Tap proposal

  • Start with element.pinchOpen(percent) and pinchClose(percent), bounded by the resolved node.
  • Use Tap’s existing 1–100 percentage convention and convert internally to AndroidX’s 0–1 value.
  • Do not promise an exact application zoom factor. Assert the app’s observable result.
  • Defer combined pan/scale/rotation transforms until there is a real Android product case.
04.9

Fling

Build with honest result
AndroidX
Uses a full-bounds fast swipe, enforces minimum fling velocity, waits for scroll events, and returns whether more content can scroll. Missing events are possible.
Appium
Exposes direction and density-scaled speed and returns canScrollMore.
agent-device
Models a fast directional throw by direction, center and distance, distinct from duration-controlled pan.

Tap proposal

  • Add selector-relative fling(direction); keep coordinates internal.
  • Prefer a typed FlingResult(canScrollMore: Boolean?) over a misleading boolean: null means Android emitted no decisive scroll event.
  • Keep speed internal or expose a small typed profile later. Raw px/s is density-sensitive API noise.
04.10

Locale

Build in two levels
Appium
Language and locale are session capabilities. This works as environment setup but makes runtime restoration and per-test isolation less explicit.
Maestro
Grants its helper CHANGE_CONFIGURATION, broadcasts the locale request, and polls persist.sys.locale with retries and a grace window.
Android 13+
cmd locale set-app-locales and get-app-locales provide a verifiable per-app override with BCP-47 tags; an empty list resets to system locale.

Tap proposal

  • First implement app.setLocales(...) on API 33+, explicitly scoped to the current Android user and verified through get-app-locales.
  • Validate BCP-47 tags before mutation and document that the app must support per-app languages.
  • Treat whole-device locale as a later managed-device feature. Capture and restore the initial locale; expect app/activity recreation.
  • Do not pretend there is a safe generic per-app implementation on API 26–32 without AUT cooperation.
04.11

Media injection

Build managed
Maestro
Streams file chunks to its Android instrumentation and inserts images/videos through MediaStore, selecting the image or video collection by extension.
Appium
Provides general file push/pull. A pushed file is not by itself a gallery/media-store contract.
Tap lesson
Because clients and daemon may be on different machines, this must stream bytes like APK installation—not accept a daemon-local path.

Tap proposal

  • Add device.media.addImage/addVideo as client-streamed RPCs with size and type limits.
  • Insert through MediaStore and return the resulting content URI plus checksum.
  • Write into a Tap-owned collection/path and track ownership so cleanup removes only Tap-created entries.
  • Start with JPEG, PNG and MP4; add formats only with device tests.
04.12

Mock location

Stateful subsystem
Maestro
Grants its driver mock-location app-op, enables platform and fused providers, and repeatedly emits locations on-device. This proves physical-device support requires persistent provider state, not one shell command.
Appium
Offers set/get/reset geolocation through its Android helper stack, with richer optional fields.
agent-device
Limits precise location setting to iOS simulators and Android emulators, choosing a narrower reliability promise.

Tap proposal

  • Do not ship a deceptively simple universal setLocation.
  • Design device.location.set()/clear() as session-owned state: establish mock-provider permission, emit updates continuously, verify, and tear down.
  • Ship emulator support first. Add physical-device support only after API 29/API 34 evidence and explicit provisioning documentation.
  • Keep route simulation, speed and bearing as later additions to the same subsystem.
04.13

Coordinate input

Reject publicly
Appium
Almost every mobile gesture accepts elements or coordinates.
Maestro
Supports absolute and percentage coordinates, though its docs prefer relative/element forms.
uiautomator2
Exposes coordinate click, drag, swipe and multi-point paths directly.
agent-device
Uses refs/selectors for agent workflows but retains coordinates as a visual fallback and for authored gestures.

Tap decision

  • Keep coordinates out of the Kotlin/Python test SDKs and recorded tests.
  • Coordinates change across density, insets, keyboards, folding state and rotation; they cannot provide NOT_FOUND or AMBIGUOUS.
  • The driver may compute points from fresh node bounds inside one command. That is implementation, not public identity.
  • If an agent-only visual fallback is ever approved, label it unsafe and keep it outside the stable test API.
04.14

WebView and Compose

Separate architecture
Appium
Discovers WebView contexts, starts a compatible Chromedriver, and proxies DOM commands after explicit context switching. This is a second automation stack with its own ports and version matching.
Maestro
Can use Android accessibility or an optional Chrome DevTools hierarchy for debuggable WebViews.
Compose
Android’s supported external-testing bridge is testTagsAsResourceId; Tap already follows this accessibility/resource-ID route.

Tap proposal

  • Continue accessibility-only WebView behavior in the core driver and document its limits.
  • If DOM automation is added, make it an explicit WebView adapter with a distinct selector namespace and lifecycle; do not hide Chromedriver/CDP behind native selectors.
  • Keep Compose on accessibility plus resource test tags by default. A direct semantics bridge would be an optional AUT-side integration, not a silent driver feature.
  • Activity-result assertions remain outside the core API; tests should assert UI, process, intent-visible, or backend outcomes.
05 / Delivery

A sequence that keeps each change provable.

Phase A

Rotation as the reference device-state operation

Additive proto, driver implementation, SDK parity, event logging, initial-state restoration, fixture screen that exposes configuration changes, and API 29/API 34 validation.

Phase B

Small device and app lifecycle actions

Screen state, deep links, background and foreground. Keep chooser interaction explicit and verify every state transition.

Phase C

Permission prompt model

Inventory controller packages/IDs on the local matrix, expose available choices, send once, and verify the prompt transition without positional fallback.

Phase D

Atomic gesture family

Double tap, selector-to-selector drag, pinch and fling. Share argument validation and pointer planning while keeping one operation per public gesture.

Phase E

Managed environment

Per-app locale, media injection and emulator mock location. Each feature ships with ownership records, cleanup, and a failure mode for unproven restoration.

Later

Dedicated automation adapters

Evaluate WebView DOM automation and a Compose semantics bridge independently. Neither blocks completing the native Android action surface.

Definition of done for every stable action: additive schema and golden wire fixture; shared validation; driver or host unit tests; Kotlin and Python APIs with documentation; agent exposure only when it is safe for agents; failure/event recording; fixture coverage; API 29 and API 34 device evidence; and updates to .docs/protocol-contract.md, .docs/server-api.md, public guides, progress, and gap records.
