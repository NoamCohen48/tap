Tap vs. agent-device, Maestro and Appium

How Tap compares with three other Android automation tools: what each is built for, how its API looks, how an action reaches the screen, what is missing on each side, and what Tap should adopt.

Based on the source code and docs of each project at its current head; nothing was run against a device. Source: .docs/competitor-comparison.md.

This project

Tap

A deterministic Android E2E engine. You write tests in Kotlin/JUnit 5 or Python/pytest against a typed gRPC server, with tap-agent, Studio and tap-watcher on the same engine.

Strength: correctness
Agents first

agent-device

A device layer for AI agents: CLI, MCP and a Node API across nine platform families. Agents explore at run time and can save replay scripts. About 352k lines of TypeScript and 39 ADRs.

Strength: agent ergonomics, breadth
YAML flows

Maestro

A flow runner with implicit waits, settling and retries. Ships Studio, an MCP server, a cloud service and AI assertions.

Strength: time to first test
The standard

Appium UiA2

W3C WebDriver for mobile, about 100 mobile: extensions, web view contexts, Inspector, Grid, and clients in every language.

Strength: breadth, ecosystem

Summary

Where Tap leads

Tap finds the element on the device and requires exactly one match in the same call that sends the input. It never replays a mutation, fences request IDs and session generations, keeps crash-resumable journals, restores every device setting it changes, and runs several devices in one test. No competitor does all of this.

Where Tap is behind

It supports one platform. It has no web views, no crash or ANR codes, no performance capture, no streamed app logs, no visual regression, no replay runner, no remote devices, no emulator boot, no telephony or biometrics, and no sharding.

Cheapest wins

agent-device's agent output: off-screen summaries, typed reason + hint + dispatched on every failure, scaled screenshots with refs drawn on, scroll movement reports, per-device capabilities, MCP instructions. All of it fits in tap-agent without changing the engine.

API comparison

The same login in each API

shop = tap_device.app("com.example.shop")
shop.cold_launch()
shop.element(res("email")).set_text("a@b.c")
shop.element(text("Log in")).tap()      # AMBIGUOUS / NOT_FOUND before any input
shop.wait(text("Welcome")).visible()     # explicit, one deadline

await c.interactions.press({ selector: 'label="Log in"', settle: true }); // returns a diff
await c.command.wait({ text: 'Welcome', timeoutMs: 5000 });

Where each API is stronger

Tap

  1. No stale state: no handles, and no refs on the test side.
  2. Selectors are typed values. A typo fails at compile time in Kotlin and at call time in Python.
  3. The Kotlin and Python surfaces match, and the gRPC contract is public.
  4. It has the most complete JUnit/pytest integration of the four.

agent-device

  1. One command registry feeds the CLI, MCP, Node and batch, so they cannot drift.
  2. Every error has a reason, a hint and a dispatched flag.
  3. capabilities lists what each device supports; batch runs N steps in one request.

Maestro

  1. Readable, diffable YAML with no programming.
  2. Composition without a language: runFlow, repeat, retry, env and tags.

Appium

  1. A standard: clients in every language, and WebDriver skills carry over.
  2. About 100 mobile: methods; a per-session Settings API.

API lessons for Tap

  • Derive dispatched: no|unknown on the client from the error code and show it with a hint in tap-agent. No protocol change needed.
  • Add capabilities() per device: which API levels gate ime_action, per-app locales and page scrolls.
  • Close the Kotlin gaps: held connections, snapshots, and JUnit device criteria (all exist in Python).
  • Don't copy: string selector DSLs, element handles, implicit waits.

Inner workings: how a tap reaches the screen

1 · findLocate the target
Tap
Driver compiles the selector to a native UiAutomator plan over all windows
agent-device
Helper captures every window's tree (6–17 ms p50); the host resolves it
Maestro
Full hierarchy dump, matched on the host
Appium
UiAutomator or XPath, handle cached
2 · gateCheck before input
Tap
Exactly one; OBSCURED from the window list; STALE_BEFORE_INPUT
agent-device
Ref-frame admission, covered-by-drawing-order, moving-target gate (still for 100 ms within 1.5 s)
Maestro
Implicit visible wait, then settle
Appium
None
3 · inputSend it
Tap
MotionEvent at the visible centre, in the same call
agent-device
UiAutomation injection at coordinates, falling back to input tap
Maestro
gRPC tap(x, y); text one character at a time, 75 ms apart
Appium
UiObject2.click() / W3C actions
4 · afterReport
Tap
Android's acceptance; the test asserts the effect
agent-device
Optional settle diff, verify, movement report
Maestro
Settle; re-tap if nothing changed
Appium
Returns

The key difference: Tap finds the element and sends the input in one call on the device. agent-device and Maestro read the tree on the host and then send coordinates, so the screen can change in between. agent-device has built a lot of machinery to close that gap: ADRs 0011, 0014 and 0039 on guarantee matrices, ref frames and pre-dispatch admission. Tap avoids most of it by construction.

What they do better

agent-device

  1. Agent output: off-screen summaries in their containers, a short answer when nothing changed, [unmeasured], truncated, scaled screenshots.
  2. Every failure says what to do next: reason, hint, dispatched, retriable, and the poll history of a wait.
  3. Gestures report what they saw (moved, at-edge, unchanged); swipes avoid the keyboard.
  4. Covered controls within one window are found from drawing order. This is Tap's open OBSCURED gap.
  5. A machine-checked guarantee matrix catches a guarantee that one code path forgot.
  6. A persistent helper cut snapshot p50 from 227 ms to 5.8 ms. Tap's equivalent cost is attach: 4–6 s per device per test.
  7. Sessions scoped to the worktree, and proof that a stale claim's owner is gone before releasing it.

Maestro

  1. Five minutes to a first test, one binary, no token.
  2. The viewer starts inside maestro mcp and prints its URL. tap-agent could offer the watcher the same way.
  3. JUnit/HTML reports, sharding and tags out of the box.
  4. Web view hierarchy merged over CDP.
  5. A crash is a result, even without a crash report.

Appium

  1. About 100 thin, independent mobile: wrappers: breadth by accumulation.
  2. Web view contexts with Chromedriver matching.
  3. A per-session Settings API for OEMs that stall.
  4. The ecosystem: Inspector, plugins, Grid.

Recommendations

A

Agent surface, client only (about a week)

  • In tap-agent output: a dispatched field and a hint on every failure, off-screen summaries, a short answer for an unchanged snapshot, --scale and --overlay-refs.
  • MCP instructions, a help tool, llms-full.txt.
  • capabilities, batch, and a reason when scroll_until stops.
B

Engine gaps that competitors treat as standard

  • Send AUT_CRASHED / AUT_ANR.
  • Detect covering views in the same window from drawing order; check set_text too.
  • Faster attach: keep the driver instrumentation alive.
  • Stream logcat with markers instead of reading the ring buffer at failure.
C

Cheap device actions, journaled with read-back

  • Emulator console: telephony, SMS, fingerprint, battery, sensors. svc bluetooth, status-bar demo mode, broadcast with extras, trim memory, .aab and split installs.
D

Medium

  • Performance evidence (gfxinfo, meminfo, Perfetto), screenshot baseline diff, Unicode typing through a test IME, emulator boot/stop.
E

Needs owner decision

  • Replay runner for tap-recording/1, web view support, human takeover hold, AI assertions, remote daemons.
